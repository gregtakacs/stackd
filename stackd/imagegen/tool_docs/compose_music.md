Compose an original song -- full mix with sung vocals -- from a style description and lyrics (YuE2). Returns a FLAC link the user can play or download, plus a link to the song's SCORE (melody, chords, key, tempo, sections -- no lyrics in it).

Use when the user asks for a song, jingle, track or music with lyrics. Not for sound effects, speech/TTS, or editing an existing recording.

Parameters:
- style: one or two sentences of music direction -- genre, mood, tempo (bpm), key instruments, vocal type (e.g. "warm female vocal", "gritty male vocal with harmonies"), production feel. Concrete beats vague: "anthemic indie rock, driving drums, overdriven guitars, male vocal, 124 bpm" beats "a rock song". For lyrics not in English, START the style with the language: "Hungarian, upbeat indie pop, ...".
- lyrics: the full lyric sheet, YOU write it unless the user supplied one. Mark sections on their own line with [Verse], [Pre-Chorus], [Chorus], [Bridge], [Outro]; blank line between sections. Write SONG lyrics -- the melody planner reads the sung sections as a shape:
  - every line 6-10 syllables, never more than 12; split a longer thought over two lines. Count the syllables, do not guess.
  - lines in a section roughly the same length (within 2-3 syllables of each other); paired lines rhyme.
  - 4 lines per verse and chorus, 2-4 per bridge (2 per pre-chorus, if the user wants one). No lists of facts, no full sentences of explanation -- one image or idea per line.
  - repeat the chorus verbatim every time. A ~3 minute song is roughly verse / chorus / verse / chorus / bridge / chorus -- NO [Pre-Chorus] unless the user asks for one: the melody planner rarely plans pre-choruses (kept in ~1 of 9 tries), so their lines get squeezed into other sections.
  - for an instrumental, still pass short section tags with no words under them.
  - talking over the music is allowed when the user wants it: tag it [Spoken] and write it as plain speech (2-4 short sentences), and add "with a spoken-word interlude over the beat" to the style -- the planner leaves that slot instrumental for the voice. For rhythmic talking use [Rap] with rhyming lines; it is planned like a verse. The line-length rules above are for SUNG sections only.
- duration_s: ONLY used with plan_melody=false (10-600, default 180) -- an upper bound there, and long lyrics with a short duration get cut. With a score (plan_melody=true or reuse_score=true) the song always runs the score's full length; leave duration_s alone. To make a song shorter or longer, write fewer or more lyrics/sections.
- plan_melody: true (default) writes a melody + chord plan (the score) first -- better structure, and the score is saved for reuse. false goes straight from lyrics to audio and leaves NO reusable score. With a plan, the server drafts up to 4 plans and keeps the first whose sections follow the lyrics (rejecting broken ones); the result's `plan` says how many it tried and whether `structure_match` is true. If it is false, tell the user some lines may be sung in a different section than written, and offer another take. If every plan is rejected you get an error: rewrite the lyrics to the rules above and call once more.
- seed: -1 for random (lets the server search plans for the best structure fit); reuse a returned seed with the same inputs to reproduce a take exactly -- a seed you pass is kept unless its plan is broken.
- cfg_scale: how strictly YuE2 follows the lyrics and style. English: leave at -1 (the model default). NON-ENGLISH lyrics: use 2.0 -- two listening rounds on a Hungarian song rated the default clearly worse, 1.5-2.0 good, and a 2.0 take best both times. With reuse_score keep seed -1 (the song's own seed): the original seed at 2.0 beat other seeds. Also raise it to 1.5-2.0 when the user asks for clearer or more literal singing. Even at 1.5-2.0 a take can swallow a short syllable; if the user hears that, offer another take (a different seed with the same score) rather than rewriting the lyrics.
- reuse_score: false (default) writes a new score. true sings the MOST RECENT saved score in this chat instead -- the same melody, chords, key, tempo and structure -- with the lyrics/style you pass now. Use it for "the same song but with different lyrics", "translate this song into <language>", "same tune, different words", "same song in a different style". The seed defaults to the original song's seed (keep it -1), which keeps the performance as close as the new words allow.

Writing lyrics for reuse_score (translations, new words to the same tune): keep EXACTLY the same section tags in the same order, the same number of lines in each section, and match each line's syllable count to the original line as closely as you can -- every syllable lands on a note of the saved melody, so a line with too many or too few syllables sounds crammed or stretched. Match the count on EACH SIDE of a mid-line pause too (a dash, or a comma where the original breathes), not just the line total: a long line is often two melodic phrases, and a word that straddles the break gets mumbled in every take (a Hungarian chorus line with the right total but 11+7 instead of the original 9+9 mumbled its split word every time). Avoid long, consonant-heavy words right at a break. Translate meaning freely to make the syllables fit; keep the chorus repeated verbatim; keep vocables like "la-la-la" as-is. Pass the original style with only what the user asked to change (e.g. the language prefix).

The score always acts on the most recent song in the current chat branch; there is no parameter to pick a different one. If the user wants an older song's tune, they branch the conversation from that song. If no saved score exists (a plan_melody=false song, or an uploaded recording), use cover_song instead.

This is slow -- expect roughly one to three minutes of generation per minute of song -- and it may first swap the image engine for the music model (and back on the next image request). Call it ONCE per request; do not retry on a slow response. Tell the user it is composing.

On success, put BOTH returned markdown links (song and score) in your final reply exactly as given, followed by the full lyrics as sung. If the result says `truncated: true`, tell the user the song is cut off at the end.
